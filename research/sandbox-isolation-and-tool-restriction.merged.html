1执行摘要

两套系统是互补关系而非竞品：deepseek-harness（下称 DSH）是「宿主框架」——以插件方式编排会话、工具、审批与执行引擎（可把 Claude Code / Codex 作为外部引擎嵌入）；codex-main（下称 Codex）是「执行核心」——自带沙箱、审批、工具注册表的 Rust 单体智能体。两边的调研结论在沙箱词汇上惊人地同构，在白名单原语的设计哲学上则方向相反：

① 沙箱词汇同构，默认哲学相反。两边都是 read-only / workspace-write / danger-full-access 三档。但 Codex 默认 read-only（受信任目录才升 workspace-write）且默认断网；DSH 出厂默认 workspace-write 且沙箱不管网络——网络管控是 DSH 二次开发必须自行补的最大缺口。
② 白名单原语一硬一活，互不可替代。Codex 的 ToolPolicy 是「启动上限」：宿主在 StartThreadOptions 注入，会话内一次性捕获、不可变、白名单外工具不进注册表也不进 tools 数组，运行期兜底报 unsupported call——最硬的白名单，但目前只是 Rust 进程内 API，app-server 协议与 TS/Python SDK 均未暴露。DSH 的 tools.restrict({allow/deny}) 是「运行时作用域过滤」：每 agent 作用域、链上交集、可见性=执行权、返回 disposer 可动态调整——更灵活但约束力以框架为界。
③ 可见性设计结论相反，值得对照记忆。DSH 把「可见」与「可执行」绑死为不变式；Codex 把曝光（ToolExposure，Deferred/Hidden 等）与执行解耦，并明确警告 exposure 不是安全边界（dispatch 不检查 exposure）。两边殊途同归：可见性手段都不能当权限边界，权限必须落在注册期或执行管线。
④ 共同缺口：都没有用户/租户身份体系。两边的策略状态都是 per-session / per-thread，没有 principal。最接近 per-user 动态下发的是 Codex 的「每线程注入 ToolPolicy」（per-thread feature 还有 gRPC 覆盖通道）与 DSH 的「创建会话时选 Agent Preset」。
⑤ 推荐架构同构，可合并为统一五层模型。两边各自的推荐组合（Codex：ToolPolicy + MCP enabled_tools + sandbox/approval + hooks；DSH：Preset 组合 + tools.restrict + 权限预设 + guard/审批）逐层一一对应，见 §6；若以 Codex 为执行核、DSH 式框架为宿主，五层可完整拼合，唯一的协议级补丁是给 app-server ThreadStartParams 加 tool_policy 字段。

3.4 旁路条件对比

Codex 报告归纳了 6 类合法旁路：① 显式 danger-full-access / --yolo；② 声明外部沙箱（ExternalSandbox，无容器嗅探，只能显式配）；③ 平台能力缺失（报错而非裸跑，Windows 走降级）；④ 审批通过的单命令豁免（第一次尝试不进沙箱）；⑤ 拦截后同意重试；⑥ 反向特例——managed network 要求时强制上沙箱。框架的哲学是把所有旁路收敛到「显式配置或用户批准」两个关口。

DSH 的旁路面窄得多：danger-full-access 档直通本地执行；bash-local/pwsh-local 不隔离执行器（换装即失去沙箱，属于部署选择）；引擎内命令走引擎原生沙箱与引擎自身的旁路规则。沙箱后端缺失时没有「降级」只有 fail closed。二次开发建议沿用 DSH 的窄旁路面 + Codex 的「旁路全部显式化」审计思路。

3.6 会话/引擎隔离（DSH 特有的「嵌入隔离」层）

Codex 单机运行时使用全局 ~/.codex。DSH 把外部引擎嵌入时的隔离做成了现实范例，也是合并方案的关键参考：

  • Claude 引擎：profile 级 $DSH_HOME/engines/claude（0700）作 CLAUDE_CONFIG_DIR；会话靠持久化 native session id 绑定（重放校验 cwd）；宿主只镜像 CLAUDE.md / skills / settings.json 的 permissions 段（进程级快照），凭据与其余字段不镜像；完全权限会话清除镜像权限防止复权。
  • Codex 引擎：每会话独立 home session-homes/<sha256(sessionId)>（0700）+ 独立 sqlite/log；恢复时校验 rollout 的 id 与 cwd、拒绝多义；宿主 config.toml 只镜像权限/信任/项目文档字段与 rules/*.rules（进程级快照、重启发条），模型/提供者/MCP/凭据字段永不进入会话 home；完全权限剥离权限字段与规则。
  • 凭据与环境：所有子进程从 scrubbedParentEnv()（剔除 KEY|PASSWORD|SECRET|TOKEN 与全部 DSH_*）起步；引擎凭据仅经 owned env 注入，部署配置禁止覆盖保留键。

证据：subagent-claude-code/src/engine.ts:494-525、user-memory.ts:41-83；subagent-codex/src/storage.ts:33-101、user-config.ts:104-134、engine.ts:500-505；subprocess/src/index.ts:40-80

这一层与 Codex 报告的「ToolPolicy 协议缺口」互相印证：DSH 正是走 app-server 接入 Codex 的宿主，因为协议里没有 tool_policy 字段，DSH 用「宿主权限规则镜像 + 原生审批路由」替代了白名单注入。若在 app-server 协议补上 tool_policy，DSH 的 subagent-codex 引擎即可把会话白名单直接下发到引擎注册表，形成端到端白名单。

覆盖面仅 DSH 原生工具（ctx.tools 注册表）；管不到外部引擎内部工具覆盖所有工具来源：内置、MCP（namespace）、hosted specs、Code Mode 生成工具（需显式列入 exec/wait）
参考实现/测试委派子代理 toolFilter（child-agent.ts:226）+ 审批钉死 never = 现成「受限主体」模板guardian-reviewer 白名单（settings.rs:31-43）；端到端测试 managed_threads_tests.rs:255-353
协议暴露会话创建 API 可带 preset/权限预设，链路完整仅 Rust 进程内 API；app-server ThreadStartParams 与 TS/Python SDK 无字段，需自行补协议
选型直觉：要「最硬」的白名单（模型连看都看不到、启动后不可放宽）选 ToolPolicy 形态；要「最活」的白名单（运行中按用户/场景动态调整、按 agent 差异化）选 restrict 形态。合并方案里两者不冲突：Codex 作执行核时 ToolPolicy 是骨架，DSH 作宿主时 restrict 管原生工具、ToolPolicy（经补丁后的协议）管引擎工具。

4.3 可见性原语的安全定性（方向相反的教训）

DSH：可见性 = 执行权

被 restrict 的工具同时从 prompt schema 与 dispatch 消失，不存在「看不见但能调」的旁路。框架不变式写入执行管线（resolveExecution → UNKNOWN_TOOL）。曝光层不存在独立概念，因此没有「用曝光当权限」的误区空间。

Codex：曝光与执行解耦，并明示危险

ToolExposure（Direct/DirectModelOnly/Deferred/CodeModeOnly/Hidden）只控制出现在哪些模型可见面；Deferred 工具的 runtime 始终留在 registry，dispatch 不检查 exposure——模型不经过 tool_search 直接 FunctionCall 也能执行。报告原话：exposure 不能当作安全边界，白名单必须落在注册期（ToolPolicy）。

4.4 MCP 与外部工具面

DSHCodex
命名mcp__<server>__<tool> 确定性命名，冲突加 12 位哈希后缀；注册冲突整代回滚（防命名抢注）namespace=服务器名（可开 mcp__ 前缀），同名消毒 + sha1 后缀；展示名 namespace__name
per-tool 过滤mcp-client 无配置项——靠 tools.restrict 精确名单或组合层不挂载per-server enabled_tools（显式白名单）/ disabled_tools（黑名单后生效）/ per-tool approval_mode（Auto/Prompt/Writes/Approve）/ omit_tools_from；另有 AppToolPolicy 多级优先级

4.5 组合层：怎么决定「最初有哪些工具」

DSH：Agent Preset（未注册即不存在）

preset = 一组插件行，装载哪些工具插件决定工具面——第一道也是最可靠的闸门。会话创建时经 agentPreset 选择，首条用户消息后锁定、创建后不可换（ApiSessionPresetConflict）。受限主体模板：子代理委派时 toolFilter → restrict + approval 钉死 never + 策略创建时定格。

Codex：features / profiles / per-thread 覆盖

[features] 枚举逐项开关（shell_tool/view_image/multi_agent/memories…）、web_search=disabled、[tools].*；[profiles] 组合成受限档案。局限：粒度粗（apply_patch 无开关）、unified_exec 普通配置关不掉（强制开启且 one-shot exec 保底）——纯配置无法真正阻止命令执行；per-thread feature 可经 gRPC 远端下发，可作按用户裁剪的补充。

5专题深挖：跨会话文件隔离与 bash 逃逸（2026-10-05 补充）

针对二次开发最常被追问的两个安全问题做专项核查：① 不同会话的文件读写是否隔离（尤其 /tmp 下的临时文件）；② 能否禁止运行未注册的工具，尤其是通过 bash 运行。核查结论：两个方向上两套系统的现有机制都不完整，需要补充设计。本节结论已同步补入两侧源报告（DSH 报告新增 §5；codex-main 两份报告各新增补充章节）。

5.1 专题一：跨会话文件读写隔离（/tmp 共享问题）

结论：两套系统的会话隔离都不包含"文件系统副作用按会话隔离"，/tmp 是全机共享路径。workspace-write 会话之间可互相读写对方的临时文件；read-only 会话不可写但可读面不受限——同 UID 下跨会话读取在任何模式下都成立。唯一的会话粒度实现是 DSH 的 Windows 后端。
维度DSHCodex
workspace-write 可写根会话 cwd + /tmp + os.tmpdir()（roots.ts:54）——全机共享工作区 + /tmp + $TMPDIR + 额外 writable_roots（permissions.rs:819-874）；macOS 另显式放行机器共享的 /private/tmp、/private/var/tmp scratch（seatbelt_scratch.rs:31-33）
子进程临时目录重写POSIX 无（继承宿主环境；ENV_OVERRIDES 仅 NO_COLOR/TERM/PAGER 等）无（TMPDIR/TEMP/TMP 属直通核心变量，shell_environment.rs:165,197；spawn.rs:52-93）
会话私有临时目录Windows 例外：workspace-write + sessionId 时每会话物化随机私有临时目录 + 独立写 SID，runner 重写 TMP/TEMP，其他会话的共享 SID 进不来（sandbox-local/src/index.ts:369-430）；read-only/缺 sessionId 回落共享 tmpdir全平台无（core 内 TempDir 仅测试使用）
剔除共享 /tmp 的旋钮无有 exclude_slash_tmp / exclude_tmpdir_env_var（config_toml.rs:865-887），但只剔除、无替代：剔除后被沙箱命令没有任何可写临时路径，依赖临时文件的命令失败
读方向隔离都没有：read-only 只 deny 写，可读面不受限；同 UID 文件级读隔离不存在（需低权专用用户 / 每会话容器）
框架自身落盘spill 输出溢出根是进程级 mkdtemp 0700 目录（spill-local/src/store.ts:36-40）——同进程所有会话共享，同 UID 的 bash 可读到其他会话的溢出输出rollout/日志在全局 ~/.codex（单机单用户形态，无多会话部署问题域）

补齐方案（两栈通用，按成本排序）：① 每会话 mkdtemp 一个 0700 私有临时目录，重写子进程 TMPDIR/TEMP/TMP，并把可写根中的字面 /tmp 替换为该目录——最小改动、收益最大（DSH 可对齐其 Windows 后端既有做法；Codex 的最小侵入改法是让 :tmpdir/:slash_tmp 解析支持会话作用域语义）；② Linux 每会话 bwrap --tmpfs /tmp、macOS SBPL deny 系统 /tmp 仅放行私有目录；③ exclude_* 旋钮保留但与私有目录配套（先替代、后剔除）；④ 读隔离靠低权专用用户运行 harness 或按会话容器化——同 UID 下没有文件级读隔离；⑤ 多会话部署把 spill/attachment 等框架自落盘目录按会话分目录；⑥ 验收标准：双 workspace-write 会话交叉验证"A 写 B 读不到"（两栈 POSIX 当前都会失败，这正是要修的）。

5.2 专题二：bash 是白名单的逃逸通道（经 shell 运行未注册工具）

结论：工具白名单约束的是"模型面前的工具清单"，不是"机器上能发生什么"。只要 shell 类工具在白名单里，模型就能调用任何未注册工具的等价 CLI（bash: curl 代替 web_fetch、bash: gh 代替未注册 git 工具），甚至 codex exec 起嵌套智能体。OS 层两边都没有二进制白名单（Seatbelt (allow process-exec)、bwrap/landlock 只限文件与网络、Windows 不限 .exe）——命令层闸门只能靠命令前缀策略。
维度DSHCodex
"任意执行"面四个，必须整体取舍：bash、pwsh、terminal_*（持久终端）、run_code（PTC：受沙箱策略约束的新 Node/Python 进程执行模型编写的程序）exec_command / unified exec（shell 类工具组）
命令策略引擎无内置：guard 包只有重复提醒与超时（均不拦截）；bash 工具只有沙箱模式 + 逐调用审批，没有"允许哪些命令"的概念——命令白名单必须自建（pre-execute 监听 / tools.guard 做 argv 前缀白名单）exec_policy 现成：Starlark prefix_rule 按 argv 有序前缀匹配（首 token = 程序名，bash -lc 包装先拆内部命令再匹配，exec_policy.rs:876-904），裁决 Forbidden/Prompt/Allow（:394-460）
无规则时的默认姿态（无此概念）空策略 → 未匹配命令回落危险命令启发式 + 审批策略：rm -rf 类 Prompt/Forbidden，其余在受限沙箱 + OnRequest/Granular 下默认允许在沙箱内执行（exec_policy.rs:770-855）——是"沙箱兜底的宽松"，不是命令白名单
中央下发无（自建策略服务）requirements overlay（MDM/企业后端，config_requirements.rs:45-57）合并在本地规则之上（exec_policy.rs:711-715）；隔离会话只加载 requirements（session/mod.rs:616-627）；可整体忽略用户/项目规则
网络对逃逸的影响沙箱不管网络：workspace-write 下 bash + curl 默认可用，免费获得 web 类工具全部能力默认断网（两档皆 Restricted）：curl/wget 类网络逃逸默认失效，开网需显式配置
配套防御审批 ask 逐调用放行；tool/result 含完整命令文本可审计框架阻止"把 bash -c 整体加白"的自动建议（BANNED_PREFIX_SUGGESTIONS，exec_policy.rs:57-146,970-978）；Allow 规则匹配全部段时可绕过沙箱本身（:440-454），编写规则要避免宽前缀

补齐方案（合并）：① 不需要 shell 就绝不放进白名单——唯一 100% 有效的手段；② 需要时实施"工具白名单 + 命令前缀白名单"双层：ToolPolicy 管"有哪些工具"、exec_policy/restrict-guard 管"shell 里能跑什么"，缺一不可；③ Codex 栈把"用户可用 CLI 清单"翻译成 requirements exec_policy，与 ToolPolicy 在 StartThreadOptions 同时注入，嵌套 agent CLI（codex/claude）与结构复杂命令（管道/命令替换/脚本文件）默认 Prompt 或 Forbidden；④ DSH 栈自建命令前缀 guard（约一天工作量，形态参考 execpolicy），解析失败即拒绝；⑤ 网络层兜底（DSH 必须：禁 web 工具只是第一道，代理/防火墙才是边界）；⑥ 保持 shell 类工具 approval: ask 与全量命令审计。

6合并推荐：统一分层管控架构

两边推荐组合逐层同构，合并为一套五层模型，并为两层栈各标对应物：

层职责DSH 对应物Codex 对应物

5.1 选型决策指南

场景建议
要「最硬」白名单，能以 Rust 库嵌入执行核Codex core-api + ToolPolicy：宿主维护「用户/租户 → allowed_tools」映射，start_thread 注入，resume 必须重注入（否则回落不过滤）；对照 managed_threads_tests.rs:255 写回归。零协议改动，一天可跑通。
经 app-server / TS / Python SDK 接入 Codex补协议字段：ThreadStartParams/ThreadResumeParams 增加 tool_policy，在 thread_processor 构建 thread_extension_init 处解析注入；展示层全名（如 mcp__github__create_issue）由宿主拆分。白名单条目务必用 tools/list 实际返回名回填。
多引擎（Claude + Codex）统一管控的宿主框架DSH 形态：preset + restrict 管原生工具；引擎侧用启动参数映射（Claude SDK options / Codex 沙箱审批）+ 权限镜像；若补了 tool_policy 协议，则把会话白名单直达引擎注册表，形成端到端白名单。
需要运行中动态调整工具面DSH restrict 的 disposer 模式，或 guard 实时查策略服务；Codex 只能靠 hook（新线程生效）——ToolPolicy 天生不可放宽。
网络合规要求Codex 沙箱自带（默认断网）；DSH 必须自建（禁 web 工具 / 代理 / 防火墙），并在白名单里剔除 web 类工具作为第一道。
按用户/租户下发策略两边都需自建 principal；建议在会话创建边界落「用户 → 工具集 + 权限预设」映射（DSH：agentPreset + 服务端网关限制可选 preset；Codex：每线程注入 ToolPolicy + per-thread feature）。

5.2 MVP 步骤（合并版）

  1. 定骨架：选定执行栈后，先落 L0+L1——Codex 栈：ToolPolicy 注入（Rust 嵌入零改动 / 协议补小字段）；DSH 栈：受限 preset + agent setup 中 restrict({allow})。以 allow 白名单为准（默认拒绝），不用 deny 枚举。
  2. 补细化：MCP 服务器侧启用 enabled_tools/disabled_tools（Codex 原生配置；DSH 把 mcp__* 名单并入 restrict）。
  3. 锁执行面：生产默认 read-only 或 workspace-write + ask；完全关闭 danger-full-access 的用户可达性；DSH 栈另需处理网络（Codex 栈默认已断网）。
  4. 上审计：L4 hook/guard 记录每次调用的策略判定；两边的授权记录已天然落会话日志，补一个监听即可闭环。
  5. 写回归：对照 Codex managed_threads_tests.rs:255-353 / DSH engine-endpoint 权限切换测试的形态，验证「白名单外不可见、调用被拒、启动后不可放宽、resume 后策略仍生效」四条。

7安全检查清单（合并）

  • 默认拒绝：L0 不装载未批准工具；L1 显式 allow 白名单。绝不以 prompt 约束替代任何一层。
  • 可见性原语不作权限：Codex ToolExposure（Deferred/Hidden）不是安全边界；DSH 的曝光与执行虽绑定，权限语义仍以 restrict/注册期为准。
  • 保留 fail-closed：不把 DSH 的 bash-sandbox 换成 bash-local；不设 danger-full-access 默认；沙箱后端探测与不可用报错保持开启；Codex 栈注意 Windows Disabled 的自动降级是否符合预期。
  • resume 即重注入：Codex 冷 resume 不持久化 ToolPolicy——把「resume 必带 policy」做成宿主 API 契约（或上游持久化到 rollout）。
  • 白名单条目以实名为准：MCP 消毒/哈希后缀、mcp__ 前缀开关、Code Mode 生成工具（exec/wait）都要按 tools/list 回填。
  • 引擎双写：DSH 宿主的 restrict 管不到 Claude/Codex 内部工具；引擎侧机制（SDK options / 原生审批 / 权限镜像）必须同时配置，并接受「宿主审批不能推翻引擎原生 deny」。
  • 升级语义收紧：面向最终用户取「梯度受限 + allowed-once + turn 内审计」；评估是否接受 Codex 的「批准后绕沙箱首跑」与 ApprovedForSession 缓存。
  • 审批通道唯一化：只保留目标应答器（web UI 等）；DSH 的 never 在服务内先决、Codex 的 never/granular 确认不被旁路配置削弱。
  • 环境变量不是权限边界：凭据走凭据服务；DSH 的 scrub 是纵深防御而非访问控制。
  • 会话间临时文件隔离：并发会话使用会话私有临时目录（重写 TMPDIR/TEMP 并替换可写根中的 /tmp）；验收做双会话交叉验证；读隔离按低权用户/容器评估。
  • shell 命令白名单：白名单含 shell 类工具时，必须有命令前缀策略（Codex：requirements exec_policy；DSH：自建 guard），结构复杂命令升级审批，嵌套 agent CLI（codex/claude 等）默认拒绝。
  • 网络出口受控：DSH 沙箱不管网络——禁 web 工具 + 代理/防火墙落地；Codex 确认 network_access 未被误开。
  • 硬隔离需求走 seam 替换：不可信代码执行上容器/microVM/远程执行（DSH sandbox-ssh 或 Codex ExternalSandbox 显式声明），应用层补丁不构成边界。
  • 防篡改特判：DSH 栈可借鉴 Codex 的「可写根下 .git/.agents/.codex/.aws 强制只读」，在可写根策略中加入保护名单。
