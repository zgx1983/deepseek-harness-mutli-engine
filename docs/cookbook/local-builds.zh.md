# 日常本地构建

[English](local-builds.md) | 中文

## 同时构建两个应用

日常迭代使用 `pnpm run build:local`。它生成 Web、Desktop、工作区依赖包和本地插件的一套协调产物，不提供应用或编译面选择：仅在内容验证通过后复用未变化的产物；工作区包变化时，将 dependency、development、peer 和 optional dependency 声明中的全部传递消费者纳入重建。TypeScript 保留增量项目构建信息；tsdown 仅打包受影响的工作区包。运行输入变化后重建 Web 和 Desktop，并刷新所有带 `build.mjs` 入口的本地插件，因为插件浏览器 bundle 可能内联共享代码。Desktop 开发运行目录会创建或刷新，供 `dsh-start` 等启动入口使用；复用未变更的构建产物时也会执行。

| 情况 | 命令 | 行为 |
|---|---|---|
| 日常迭代 | `pnpm run build:local` | 检测输入变化、重建依赖和两个应用，复用验证通过的未变化产物。 |
| 强制建立新的协调基线 | `pnpm run build:local -- --full` | 完整仓库构建、本地插件构建及最终 Desktop 构建。 |
| 官方客户端构建 profile | `pnpm run build:local -- --profile official` | 使用指定公开客户端环境生成协调产物；环境变化时需要完整基线。 |

首次运行执行完整基线构建。增量 Client 构建同时选择包的库配置和 `/client` 浏览器打包配置。产物缺失或内容变化、依赖或根编译配置变化、native 变化、共享打包配置变化、构建脚本变化，以及运行时或公开客户端环境变化都会使基线失效。删除包也会使基线失效。如果构建输入未变化且产物哈希一致，两个应用复用此前成功生成的产物。缓存位于 `.dsh-build/local-build.json`，仅供本机使用且可丢弃，所有阶段成功后才保存。阶段失败会阻止后续阶段并删除缓存。构建期间输入发生变化时，不接受此次产物；停止编辑后重新运行。协调构建成功后才写入完整客户端产物记录。

运行协调构建前，停止构建监听和其他构建进程。日常迭代之间不要运行 `clean`，也不要修改缓存绕过验证。该命令不打包安装程序、不修改用户 profile、不启动服务，也不替代功能要求的行为测试和会话快照。Desktop 准备复用共享 Electron 缓存，首次使用可能下载 Electron；它只准备工作区链接和发布元数据，不启动 Electron，也不准备主解释器运行时。native 构建失败仍会失败；包的构建依赖声明不正确时，仍需修复清单。原有按编译面构建的命令继续供诊断使用，但不是日常协调构建流程。应用启动方式见[开发命令](../development.zh.md)。

## 减少输出

所有构建工具遵循项目[命令执行与结果反馈规范](../command-execution.zh.md)。下文说明当前包装入口的输出和构建特有的成功预期。

`build:local` 使用 `build:quiet` 包装入口。完整输出写入 `.dsh-build/build-logs/` 下的独立文件，该目录被 Git 忽略。成功时仅显示状态、耗时和日志绝对路径。失败时保留退出码，仅显示最后 12000 字节中的末尾 80 行。如果原因出现在更早的位置，应搜索保存的日志，只将相关诊断交给智能体。产物缺失或冒烟检查失败需另外检查；编译成功不能代表这些检查通过。

`pnpm run build:quiet -- <script> [arguments]` 也可不通过 shell 包装其他有限运行的根 package 脚本。长期运行的监听输出应保存到文件；常规进度检查应读取进程状态，不应反复打印日志末尾。调查完成前保留日志，不再需要时删除旧文件。包装入口不脱敏，也不改变被调用脚本。

## 给模型的执行步骤

适用场景：用户要求完成日常迭代后构建 Web、Desktop 及其依赖；从当前仓库根目录执行。先读本仓库的 `AGENTS.md`，保留用户改动，不清空用户数据。

1. 完成源码编辑，停止自己启动的构建监听；确认没有其他构建或源码写入仍在进行。不终止不属于本任务的进程。
2. 执行 `pnpm run build:local` 并等待结束。首次运行会自动完整构建；除非用户要求或需要诊断缓存问题，否则不加 `--full`。
3. 成功时只记录退出状态、耗时和日志路径，不读取或输出完整日志。运行较久时检查进程状态，给用户简短进度，不反复打印日志末尾。
4. 失败时停止验收，读取包装入口给出的有限错误片段；信息不足时在对应日志中搜索错误并读取必要上下文。修复后重跑同一入口。遇到沙箱权限失败，按 `AGENTS.md` 原样申请最小范围的宿主执行；不跳过失败步骤。
5. 确认命令成功，再做任务要求的产物或运行验证。构建不会自动启动应用；只有用户要求时才通过支持的入口启动。报告实际执行的检查、失败和未完成项，不把“构建成功”写成“功能验证通过”。

如果出现 `source changed during the build`，本轮不能作为有效增量基线。等待源码和构建脚本稳定后重新执行，不手写缓存或产物记录，也不把单独执行 `build:web` 或 `build:desktop` 当作协调构建的替代品。

## 检查范围

| 项目 | 是否由轻量构建执行 | 模型应如何处理 |
|---|---|---|
| 受影响项目的 TypeScript 编译检查 | 是 | 任一编译错误都阻止构建成功。 |
| Web、Desktop、受影响依赖和本地插件构建 | 是 | 两端必须形成一致产物；不能只完成一端。 |
| 定向 lint、行为测试 | 否 | 根据源码改动运行相关文件的检查，不默认执行全量测试。 |
| 完整 typecheck、lint | 否 | 根据公共接口变化和仓库规则决定；当前脚本自身会先构建 Host。 |
| doc-sync、文档配对和链接检查 | 否 | 根据文档改动执行，完整日志保存到文件。 |
| 会话快照、真实 API 测试、应用冒烟 | 否 | 按改动影响及任务要求执行，分别报告结果。 |

其他有限运行的根脚本可用 `pnpm run build:quiet -- <script> [arguments]` 保存日志，例如 `pnpm run build:quiet -- doc-sync`。该入口只减少输出，不缩小检查范围；不要因为日志少就默认运行昂贵的全量检查。
